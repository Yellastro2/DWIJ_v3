# Project Notes For Coding Agent

## Идентичность проекта

- Название репозитория: `DWIJ_v3`.
- Пользовательское название Android-приложения: `Движ`.
- Тип проекта: многомодульное Android-приложение — музыкальный клиент и плеер с интеграцией Яндекс Музыки.
- Основной стек: Kotlin, Java, Android SDK, XML Views, AndroidX Fragments и Navigation, Kotlin Coroutines, Room, Media3 ExoPlayer и MediaSession.
- Модуль `:app` содержит приложение, UI, локальное хранилище, репозитории и сервис воспроизведения.
- Модуль `:yandexmusiclib` содержит клиент и модели интеграции с Яндекс Музыкой и Yandex ID.
- Основной пакет приложения: `com.yellastrodev.dwij`.
- Основной пакет библиотеки: `com.yellastrodev.yandexmusiclib`.
- Связанные внешние системы: API Яндекс Музыки и OAuth Device Flow.
- База знаний и референс поведения API для модуля: Python SDK `MarshalX/yandex-music-api`; путь к её локальному клону задаётся переменной `LOCAL_CLONE` в `yandexmusiclib/local.properties`.
- Не переносить сюда правила, названия, ресурсы или документацию из других проектов без явной просьбы пользователя.

## Обработка запросов

- Если пользователь задаёт вопрос, сначала ответить текстом и не редактировать файлы автоматически.
- Переходить к изменениям только после явной просьбы сделать, исправить, заменить, реализовать или удалить что-либо.
- Если запрос одновременно содержит вопрос и команду на изменение, сначала кратко ответить на вопрос, затем выполнить изменение.

## Область изменений

- Изменять только файлы, необходимые для текущей задачи.
- Не выполнять попутный рефакторинг, переименование или форматирование несвязанных участков.
- Сохранять существующее поведение вне заявленной задачи и предпочитать минимальные совместимые изменения.
- Перед изменением поведения найти реализацию, связанные вызовы, ресурсы, Gradle-конфигурацию и документацию.
- Не менять без необходимости публичные контракты `yandexmusiclib`, структуры Room, форматы данных, deep links и контракты Media3.
- Не редактировать пользовательские изменения в рабочем дереве, если они не относятся к текущей задаче.

## Структура и архитектурные границы

- UI приложения находится в `app/src/main/java/com/yellastrodev/dwij/activities`, `fragments`, `adapters` и в `app/src/main/res`.
- ViewModel-подобные модели экрана находятся в `app/src/main/java/com/yellastrodev/dwij/models`.
- Слой данных разделён на `data/source`, `data/repo`, `data/dao` и `data/entities`; сохранять это разделение при добавлении логики.
- Воспроизведение и MediaSession находятся в `app/src/main/java/com/yellastrodev/dwij/service`.
- Сетевую логику и модели Яндекс Музыки, пригодные независимо от UI приложения, размещать в `:yandexmusiclib`.
- `:yandexmusiclib` не является переводом Python SDK на Kotlin: использовать оригинал как источник контрактов и знаний об API, а интерфейсы проектировать идиоматично для Kotlin, Coroutines и Android.
- Не добиваться соответствия классов и методов Python SDK один к одному; сохранять сетевую семантику и ожидаемый результат, выбирая естественную для Kotlin/Android архитектуру.
- Не переносить Android UI, Room DAO или код сервиса воспроизведения в `:yandexmusiclib`.
- При изменении сетевых моделей проверять сериализацию, nullable-поля и обработку ошибок на границе библиотеки и приложения.

## Поиск и чтение файлов

- Для поиска файлов и текста сначала использовать `rg` и `rg --files`.
- Исключать из широкого поиска `.git`, `.gradle`, `.kotlin`, `.idea`, `build`, временные каталоги, кэши и бинарные артефакты.
- Широкий поиск ограничивать исходниками, ресурсами, Gradle-файлами и документацией: `.kt`, `.java`, `.xml`, `.gradle`, `.kts`, `.md`, `.txt`, `.json`, `.properties` и `.toml`.
- Не выполнять широкий поиск по `.db`, `.sqlite`, `.jar`, `.aar`, `.apk`, `.aab`, `.class`, архивам и изображениям.
- Если `rg` недоступен, использовать PowerShell-поиск с фильтрацией каталогов и типов файлов до `Select-String`.
- В Windows PowerShell читать русскоязычные текстовые файлы с `Get-Content -Encoding UTF8`; для `Select-String` также явно задавать `-Encoding UTF8`.
- Если русский текст отображается как mojibake, считать чтение некорректным и повторить его с явной UTF-8 кодировкой.

## Правила Kotlin и Android

- Сохранять стиль и именование окружающего кода; не проводить массовую нормализацию существующих имён в рамках несвязанной задачи.
- Для Kotlin-строк предпочитать строковые шаблоны; сложные строки собирать через понятные локальные переменные или `buildString`.
- Не выполнять сетевые запросы или блокирующие операции в main thread; использовать существующие coroutine scopes и корректно учитывать Android lifecycle.
- Для Flow и StateFlow сохранять существующие правила владения состоянием и отмены подписок.
- При изменениях Room синхронно проверять entity, DAO, converters, версию базы и стратегию миграции.
- При изменениях плеера учитывать жизненный цикл `PlayerService`, MediaSession, foreground service, уведомление и освобождение ресурсов.
- Строки интерфейса выносить в `app/src/main/res/values/strings.xml`, если они не являются техническими значениями.
- Не хардкодить токены, секреты, ключи и приватные URL. Новые секреты и локальные настройки хранить вне исходников и не коммитить.

## Тяжёлые векторные ресурсы

- Тяжёлые декоративные VectorDrawable хранить как редактируемые SVG в `app/src/main/vector-png`, добавляя имя и исходный размер в `rasterizedSvgAssets` внутри `app/build.gradle.kts`.
- Исходный XML сохранять в `app/src/main/res/drawable` с префиксом `_` только как эталон; рабочее имя `R.drawable` создаётся из PNG задачей `RasterizeSvgToPngTask`.
- Не редактировать PNG в `app/build/generated/res/vectorPng`: они генерируются сборкой. Подробности механизма находятся в `docs/svg-rasterization.md`.

## Логи и чувствительные данные

- Для Android-кода использовать `android.util.Log` и существующий осмысленный `TAG`.
- Новые и изменяемые сообщения логов писать на русском языке и начинать с контекста функции или этапа в формате `[functionName]`.
- Не логировать access token, auth token, полные заголовки авторизации, cookies или другие секреты. При диагностике допустима только безопасная маскировка.
- Логи должны помогать разбирать состояние плеера, БД, API и жизненный цикл, а не дублировать очевидный код.

## Проверка

- Не запускать Gradle, `gradlew`, `gradlew.bat` или сборку Android Studio: Gradle-команды в этом проекте запускает пользователь.
- Проверять изменения статически: связанные вызовы, импорты, сигнатуры, ресурсы, manifest, зависимости и согласованность между модулями.
- В Compose-коде не добавлять явный импорт `androidx.compose.foundation.layout.weight`: в используемой проектом связке он может разрешиться во внутреннее свойство `RowColumnParentData.weight` и сломать компиляцию. Вызывать `Modifier.weight(...)` только внутри `RowScope` или `ColumnScope`, где extension доступен через scope без отдельного импорта. После правок Compose проверять через `rg`, что такого импорта в исходниках нет.
- В итоговом сообщении указывать, какие проверки выполнены, и явно сообщать, что сборка и тесты не запускались из-за правила проекта.
