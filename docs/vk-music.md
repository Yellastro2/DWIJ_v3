# ВК Музыка: поиск и плейлисты

## Навигационный каталог VK (2026-10-07)

Вкладка «Каталог» при выбранном VK показывает четыре карточки в общем стиле:
«Мои треки» → `VK_MY_TRACKS`, «Все треки» → `VK_ALL_TRACKS`, «Плейлисты» →
существующая сетка VK и «Рекомендации» → `VK_RECOMMENDATIONS`.
`CatalogScreen.VkCatalogContent` содержит только переходы; при открытии вкладки
дополнительных API-запросов нет. Артисты, альбомы, жанры и внешняя лента VK
в этом сценарии не показываются. Составы загружают уже существующие экраны.

## Рекомендации (2026-10-07)

На главной при выбранном VK карточка «Рекомендации» заменяет «Волну» и открывает
`VkRecommendationsRoute` с четырьмя плитками: «Рекомендации», «Для вас»,
«Открытия», «Новинки». Используются те же `PlaylistGridScreen` и `PlaylistGridItem`,
что у ЯМ-волн. Все карточки сразу имеют разные локальные текстурные фоны.
При открытии сетки в фоне запрашиваются только метаданные `catalog.getAudio`:
обложки трёх generated-подборок заменяют локальные фоны. Составы не загружаются.
«Рекомендации» остаётся с локальным оформлением, отдельной обложки в API нет.

- «Рекомендации»: по нажатию `audio.getRecommendations`, затем общий VK-треклист.
- «Для вас», «Открытия», «Новинки»: по нажатию получают актуальные ключи
  generated-плейлистов `-21`, `-24`, `-23`, затем состав через `audio.get`.
  Каталожный `count=0` не блокирует запрос треков.

Карточка «Каталог», «Обзор», «Обновления» и вложенные разделы удалены из этого
сценария по уточнению пользователя. `catalog.getAudio` используется только как
источник метаданных трёх персональных подборок; `catalog.getSection` не вызывается.
`VkRecommendationCatalog` разбирает ответы; `VkMusicRepository.getPlaylist()`
обрабатывает отдельное пространство `vkrec:` без добавления подборок в личные
плейлисты. `VkPlaylistModel` удерживает список при возврате из плеера и не запускает
попутное обновление личной фонотеки. Общий VK-экран сохраняет воспроизведение,
скачивание и добавление треков; редактирование/удаление подборок запрещено.
Смена сессии очищает экран и не принимает старый результат загрузки.

Диагностическая кнопка с дампом JSON заменена этим экраном после изучения
пользовательского лога. VK Микс отложен в `roadmap.md`, его запросы не вызываются.
Живой лог подтвердил разбор списка рекомендаций и метаданных каталога;
загрузка составов generated-плейлистов и новые переходы требуют проверки пользователем.

## Подключение

`vkMusicSdk/` — независимый Kotlin/JVM SDK (Android и desktop, JVM 11).
Он не зависит от shared, Android, JavaFX или yaMusicSdk. Shared подключает его через
`api(project(":vkMusicSdk"))`; оба приложения получают его через shared.
SDK теперь отдельный Git-репозиторий, подключённый субмодулем. Изменения SDK
коммитятся и публикуются в нём, затем обновляется указатель в репозитории Движа.

- `VkApiClient`: token-based POST, отмена HTTP вместе с coroutine, `api.vk.com`, версия 5.199;
  audio.search, getSearchSuggestions, catalog.getAudio/getSection, audio.add/delete.
- Дополнения по vkpymusic: audio.getById, пагинация плейлистов/треков,
  рекомендации. SDK возвращает каталог сырым JsonElement; shared разбирает его
  для обложек персональных рекомендаций и ключей выбранной подборки.
- `VkOAuth`: OAuth Маруси из README LavaSrc, без клиентского секрета и cookies.
- `VkWebSession`: отдельная браузерная сессия p/remixsid, web-токен и Unix-срок;
  `VkApiClient` умеет обновлять её перед запросами, не меняя токенный OAuth-путь.
- `VkHlsRelay`: ограниченный текущим воспроизведением loopback-сервер для VOD HLS;
  relative URI, master playlist, AES-128, смена ключей, sequence/explicit IV,
  MAP и BYTERANGE. Нет перекодирования; поддержка контейнера зависит от плеера.

## Межсурсные совпадения VK (2026-10-03)

VK участвует в существующем `SongMatchRepository`, без отдельного resolver-модуля,
новых таблиц или изменений SDK/плееров. Версия общего сканирования повышена до 2:
при запуске пересматриваются уже индексированные песни, затем новые/изменённые записи.
С 2026-10-05 внизу общих настроек Android/Windows доступно «Сканирование мультисурсов».
По умолчанию включено; ключ `multi_source_scan_enabled` сохраняется в существующем
`LocalKeyValueStore`. Отключение отменяет наблюдаемый скан и прекращает CPU-сравнения
между парами, оставляя незавершённые песни в очереди. Повторное включение запускает
наблюдение заново и обрабатывает накопленные записи. Найденные кандидаты, решения
пользователя и подтверждённые группы сохраняются; получение музыки не отключается.
Добавлены Room-проверки восстановления настройки, сохранения очереди/кандидатов,
возобновления и остановки внутри сравнения; Gradle и тесты агентом не запускались.
Скан сравнивает только метадату в Room, не ищет дополнительные треки в интернете.
VK попадает в индекс при чтении фонотеки/плейлиста, воспроизведении или сохранении;
сама выдача поиска целиком в индекс не записывается.

Предлагаются VK ↔ ЯМ, VK ↔ local и VK ↔ подтверждённая группа ЯМ + local.
Группы с пересечением источников, включая VK ↔ VK, не сравниваются.
Для пар с VK `SongMatchResolver.compare(checkRecording = true)`:

- сохраняет существующую fuzzy-оценку названия и исполнителей;
- разделяет строку artist по feat./ft., запятой и разделителям с пробелами, чтобы
  сопоставлять её со структурированным списком артистов;
- отклоняет известные положительные длительности с разницей больше 10 секунд;
- отклоняет разные наборы пометок версии в названиях: live, remix/mix, acoustic,
  instrumental, karaoke, cover, sped up, slowed, radio edit, extended, remaster.

Это эвристики для подсказок, не доказательство идентичности записи. Неизвестная
длительность не блокирует кандидата, неуказанная в названии версия не определяется.
Для пары ЯМ ↔ local прежние правила сравнения сохранены.

Кандидаты появляются в существующем экране «Варианты совпадений» и диалоге источников.
При выключенном автослиянии объединение выполняется после выбора пользователя через
`SongRepository.mergeInstances`: одна Song, исходные source-ID и полные инстансы.
«Это разные песни» сохраняется как REJECTED и не отменяется пересканированием.
Коллекции VK, лайки ЯМ и offline-файлы от объединения не меняются.

С 2026-10-09 в той же карточке настроек есть «Автослияние вариантов», по умолчанию выключено.
Ключ `multi_source_auto_merge_enabled` сохраняется в `LocalKeyValueStore`; включение требует
подтверждения обработки текущих и будущих предложений. Отмена оставляет настройку выключенной.
`SongMatchRepository.start` отдельно наблюдает PENDING-пары даже при выключенном скане.
Скан и слияние сериализованы одним mutex; перед слиянием повторяется проверка метадаты.
`SongMatchDao.mergePendingCandidate` транзакционно проверяет статус, наличие обеих Song
и отсутствие пересечения источников, затем вызывает общий `SongDao.mergeInstances`.
Предложения и отказы удаляемой Song переносятся к оставшейся группе; REJECTED имеет приоритет,
поэтому цепочка объединений не теряет следующий вариант и не обходит отказ.
Текущая очередь обновляется через `PlayerRepository.applyMergedSong` на Main без перезапуска аудио.
Отключение прекращает следующие слияния и не разъединяет уже созданные группы.
Room-проверки покрывают восстановление настройки, накопленные/новые пары без скана,
цепочки, перенос отказов и пересекающиеся источники. Добавлены без запуска Gradle.

`VkSongMatchResolverTest` проверяет длительность, версии, artist credit и прежний
режим сравнения; `VkSongMatchRepositoryTest` — пересканирование, независимые пары,
пользовательский отказ и сборку VK-очереди после подтверждённого объединения в Room.
Тесты и сборка агентом не запускались. Проверить в Android и Windows: загрузить
VK-плейлист с известным ЯМ/local-треком, открыть кандидата, подтвердить объединение,
проверить переключение источника и очередь, перезапустить приложение; отдельно
отклонить пару и убедиться, что отказ сохранился.

## Вход и поиск

### Дополнительный Android-вход через сайт VK (2026-10-04)

Кнопка «Войти через сайт VK» открывает отдельный `AndroidVkWebLoginBrowser` на
`https://vk.ru/` с фактическим Android User-Agent WebView. OAuth Маруси,
`AndroidVkLoginBrowser`, его callback/state и внешний ручной вход сохранены.
Windows-вариант добавлен отдельно 2026-10-05 через WebView2, см. следующий раздел.

После обычного входа CookieManager нативно читает p/remixsid из основной/login/mobile
областей VK. Переходы ограничены HTTPS-доменами VK; JS-мост, чтение пароля и ручной
экспорт cookies не используются. После страницы аккаунта вход завершается автоматически;
«Я вошёл» позволяет повторить проверку при нестандартной навигации сайта.
При ошибке проверки окно остаётся открытым. Сессия Chrome в этот WebView не переносится.
WebView Маруси и нового входа используют общий CookieManager приложения. С 2026-10-05
«Сбросить сессию браузера VK» видна в debug/release, до и после подключения аккаунта.
Пока окно входа открыто или выполняется проверка/сброс, кнопка остаётся видимой, но неактивной.
Очистка выполняется только по нажатию; сохранённая SDK-авторизация не удаляется.
Вход через Марусю и оба его варианта (встроенный/внешний браузер с ручной вставкой)
убраны из общей карточки Android/Windows. OAuth-код SDK/репозитория и платформенные
реализации сохранены; единственная видимая точка входа — «Войти через сайт VK».

`authorizeWebSession` получает web_token, проверяет audio.search и users.get и только
после успеха заменяет текущую сессию. Сохраняются authMethod=web, p, remixsid,
User-Agent, token, expiresAt, accountId и имя в существующем защищённом payload.
Старые token-only и OAuth JSON-payload читаются как раньше. Cookies WebView также
остаются в его обычном браузерном профиле; удаление карточки очищает SDK-payload,
но не вызывает глобальный выход VK и не чистит данные других WebView.

Web-клиент использует api.vk.ru, 5.282 и client_id=6287487 по vk-audio; OAuth-клиент
сохраняет api.vk.com, 5.199 и стандартный UA OkHttp. Cookies идут только в web_token,
в audio API передаётся токен и тот же фактический UA, что использовался при входе.
После восстановления сети нет до обращения к API. Истёкший или истекающий за
10 минут токен обновляется перед запросом, фонового таймера нет. Web-refresh и API
разделяют один mutex и интервал между стартами 1000 мс; обложки/медиа не тротлятся.
Ротация p/remixsid из Set-Cookie и новый токен сохраняются до использования.
Код API 5 допускает одно обновление и один повтор запроса; отозванные cookies
требуют нового входа. Обновление не может подменить владельца сохранённой сессии.
Устаревший SDK-клиент не перезаписывает payload после смены аккаунта или удаления.

Для проверки: удалить прежнюю локальную карточку, выбрать «Войти через сайт VK»,
пройти обычный вход, проверить имя, поиск и плейлисты, затем перезапуск/выгрузку
приложения и повторное обращение после истечения токена. Наблюдать сбросы безопасности
сразу и через несколько часов. Устойчивость новой схемы на аккаунте не подтверждена.
Добавлены MockWebServer-тесты обновления, ротации, параллелизма, тротлинга, кода 5,
отзыва cookies, ошибки сохранения и запрета перенаправления. Gradle, тесты и устройство
агентом не запускались по правилам проекта; требуется сборка пользователем.

Пользователь 2026-10-05 сообщил, что после перехода на этот способ почти сутки
не наблюдает прежнего сброса сессий. Это результат одного аккаунта за указанный
период, не гарантия длительной устойчивости и не доказательство причины прежних сбросов.

### Windows: вход через WebView2 (2026-10-05)

Та же кнопка «Войти через сайт VK» в desktop запускает отдельное окно
`Dwij.VkWebView2.exe` (WinForms/.NET Framework 4.6.2+, Windows x64). Оно использует
общий Evergreen WebView2 Runtime, без собственного Chromium и без доступа к профилю Chrome.
Профиль Движа расположен в `%LOCALAPPDATA%/DWIJ/vk-webview2-profile`; файлы host
извлекаются из JAR в `%LOCALAPPDATA%/DWIJ/vk-webview2-host/<digest>`.
После успешного входа host закрывается; дальнейший refresh выполняет общий SDK.

`desktopApp/windows-webview2/build-helper.ps1` получает закреплённый официальный
SDK NuGet 1.0.4258.31, собирает C# встроенным csc .NET Framework и копирует Core,
WinForms и x64 WebView2Loader DLL. Gradle-задача `buildVkWebView2Helper` вызывается
из processResources; файлы попадают в JAR и обычные EXE/MSI-дистрибутивы.
Для компиляции host не нужны dotnet SDK/Visual Studio. Первый запуск сборочного
скрипта требует NuGet-сеть; повторный использует SDK-кеш в desktopApp/build.
Host с DLL/config занимает около 0.91 MiB в проверенной сборке; Runtime не включён.

CookieManager WebView2 нативно читает p/remixsid; передаёт их и фактический UA
одной JSON-строкой по приватному stdout-pipe. Kotlin не логирует этот канал,
не сохраняет cookies в аргументы/временные файлы и передаёт их в authorizeWebSession.
Состояние проверки/ошибка идут обратно через stdin; после ошибки окно остаётся
для повторного входа. Одна пара cookies не отправляется автоматически циклически.
Навигация ограничена HTTPS VK, JS-мост отключён; закрытие карточки/приложения
закрывает host, EOF родителя тоже завершает его. Mutex предотвращает два окна
с одним профилем. OAuth-код Маруси сохранён, но скрыт из общего UI; Android использует свой WebView.

На Windows кнопка сброса также видна до/после входа. Host поддерживает
`--reset --user-data <профиль>`: невидимый WebView2 без навигации вызывает
[`Profile.ClearBrowsingDataAsync(AllProfile)`](https://learn.microsoft.com/en-us/dotnet/api/microsoft.web.webview2.core.corewebview2profile.clearbrowsingdataasync).
Очистка использует тот же mutex профиля, сохраняет каталог и DPAPI payload.
Kotlin ждёт подтверждение `type=reset` на IO не более 30с; ошибка не считается успехом.
SDK-сессию удаляет отдельная кнопка «Удалить».
Нативный helper с новой командой отдельно скомпилирован 2026-10-05; реальную очистку
пользовательского профиля, UI на устройстве и полную Gradle-сборку агент не запускал.

Если Runtime отсутствует, карточка сообщает причину и предлагает официальный
сайт установки Microsoft. Автоматического скачивания Runtime или установки
при запуске приложения нет. После установки нужно открыть вход повторно.

Проверено агентом: C# host собирается штатным csc; headless `--probe` через IPC
возвращает available=true, Runtime 154.0.4258.53; diff без whitespace-ошибок.
Добавлены Kotlin-тесты протокола IPC. Gradle/Kotlin-тесты не запускались по AGENT.md.
Полный вход VK в окне, возврат в desktop, упаковка EXE/MSI и устойчивость сессии
ещё требуют сборки и проверки пользователем.

### Текущий диагностический режим Маруси: только OAuth (2026-10-04)

`VkMusicRepository.AUTHORIZATION_ONLY = true`: полученный access_token сохраняется
в защищённом хранилище без проверочных audio.search и users.get. Профиль не загружается.
SDK-клиенты при авторизации и восстановлении создаются с requestsEnabled=false:
любой API-запрос отклоняется до отправки HTTP. Для OAuth Маруси операции VK,
получение playback URI и загрузка VK-обложек отключены. Новый браузерный способ
работает обычно: `authorizationOnly` учитывает текущий тип сессии.
Карточка Маруси показывает «Только OAuth: VK отключён»;
сохранение токена в этом режиме не подтверждает доступ к музыкальному API.
OAuth-страницы, cookies браузера и существующий автоматический повтор OAuth остаются
частью эксперимента. Для проверки получить новую авторизацию и наблюдать сброс сессий
сразу и в течение нескольких часов. Простого выхода из обычной сборки после входа
недостаточно: проверочные запросы уже выполняются до сохранения токена.
Возврат обычного поведения: установить AUTHORIZATION_ONLY=false и пересобрать.
Сборка и тесты агентом не запускались.

### Обычный режим

С 2026-10-04 Движ включает `minRequestIntervalMs=1000` в `VkApiClient` при входе
и восстановлении сессии. Авторизованные API-запросы одного клиента выполняются
последовательно до получения ответа, между стартами выдерживается минимум секунда.
Первый запрос отправляется сразу; ошибки также учитываются в интервале. Ожидание
отменяется вместе с coroutine. В SDK значение 0 по умолчанию отключает ограничение.
Обложки и аудиоресурсы relay используют отдельный транспорт без этого ограничения.
Получение свежей ссылки воспроизведения является API-запросом и также ограничивается;
ожидание может расходовать существующий таймаут 8 секунд. Живая проверка ожидается.

Эксперимент 2026-10-04: API переведён с `api.vk.ru`/`5.282` на `api.vk.com`/`5.199`
по образцу LavaSrc; явный `VKAndroidApp` User-Agent убран из API-запросов, используется
стандартный UA OkHttp. Токен остаётся в теле POST. OAuth Маруси и UA загрузки
медиаресурсов HLS-relay не изменены. Проверка живых методов и длительной устойчивости
сессии ожидается; это не подтверждённое исправление сброса сессий VK.

**Наблюдение пользователя от 2026-10-04:** иногда сразу после авторизации VK,
иногда через несколько часов VK сообщает о подозрении на взлом, сбрасывает все
сессии аккаунта и требует подтверждения аккаунта и смены пароля. Причина и
зависимость от платформы/способа входа не установлены. Подробности и границы
проверки: [legend VK Music API](legend/vk-music-api.md#сброс-всех-сессий-по-безопасности-сообщение-пользователя-2026-10-04).

Авторизованная карточка VK повторяет компактную раскладку ЯМ: знак VK, название,
имя и фамилия аккаунта, кнопка «Удалить» справа. Смена аккаунта выполняется после
удаления авторизации. Имя читается через `users.get` и сохраняется вместе с токеном
и accountId в защищённом payload, восстанавливается без сети. У старой сессии без
имени профиль загружается при открытии настроек; ошибка загрузки не удаляет вход,
до получения имени отображается «Авторизация сохранена».
Сборка и проверка отображения на устройстве агентом не выполнялись.

Ниже описан прежний UI OAuth Маруси: с 2026-10-05 эти действия скрыты из карточки.
Описание сохранено для кода OAuth, который не удалялся; текущий вход описан выше в разделах веб-сессии.

1. Настройки → ВК Музыка → «Войти в VK через Марусю» (прежний интерфейс).
2. Android открывает собственный полноэкранный WebView с desktop User-Agent;
   после входа callback перехватывается автоматически. Windows открывает внешний браузер.
3. Во внешнем браузере скопировать полный URL страницы `oauth.vk.com/blank.html`
   (или oauth.vk.ru), вернуться в приложение, вставить URL, нажать «Завершить вход».
4. Callback проверяется по HTTPS origin/path (oauth.vk.com или oauth.vk.ru) и совпадению state,
   если он присутствует. Автоматический callback требует state; только при явной ручной
   вставке отсутствие state допустимо (формат из LavaSrc).
   До сохранения выполняется
   audio.search с полученным токеном. Ошибка не заменяет прежнюю сессию.
5. Главная → Поиск → источник «ВК Музыка» → запрос → нажатие на трек.

На Android `AndroidVkLoginBrowser` реализует автоматический callback через WebView;
внешний браузер остаётся запасным ручным сценарием, автоматического deep link нет.
OAuth state переживает пересоздание экрана;
URL с токеном не сохраняется в saved state. Токен не выводится в логи.
Поле показывает ссылку обычным многострочным текстом (3–6 строк) с переносом длинного URL.
Цвета кнопок, отключённых состояний и label заданы явно для тёмной карточки.
Разбор отклонённого адреса возвращает конкретную причину: неверный URL/origin,
нет части после #, нет токена, повреждённые параметры, отказ VK или несовпадающий state.
Логи `[completeVkAuthorization]` сообщают эту причину либо факт принятия ссылки
и наличие/совпадение state; сам URL, токен и OAuth error_description не логируются.

Android-проверка 2026-10-02 выявила другой ответ VK: `#payload=...&state=...`,
внутри payload `type=silent_token`, `ttl=600`, вместо `access_token`.
Этот промежуточный ответ VK ID пока не поддерживается для входа в музыку:
SDK возвращает отдельную причину `VkIdPayload`, не принимает payload.token как access_token
и не отправляет его в audio.search. Автоматический обмен silent_token не реализован.
Временно по просьбе пользователя (2026-10-03) Android WebView пишет полный callback
в debug-сборке в `[debugVkRedirect]`, частями по 2000 символов, один раз за вход.
Этот диагностический лог содержит токен/профиль; удалить после исследования обмена.
В release полная ссылка не логируется.
Первоначально сброс добавлялся только для Android debug без подключённого аккаунта.
С 2026-10-05 «Сбросить сессию браузера VK» доступна во всех сборках и при подключённом аккаунте.
Она ждёт callback удаления cookies, очищает общее
веб-хранилище и кеш WebView, отменяет pending OAuth в карточке и сообщает результат.
Следующий браузерный вход начинается без прежних cookies. Сохранённые токены SDK не удаляются;
сессии внешнего браузера и приложения VK не затрагиваются. Очистка затрагивает
общие данные всех WebView приложения. Проверка на устройстве ожидается.
Кнопка «Повторить вход» удалена по просьбе пользователя. Для определения точки
автоматического повтора OAuth добавлены `[traceVkPage]`: navigate, started, history,
visible, finished, progress100. Выводятся scheme/host/path и имена параметров,
без значений query/fragment. visible/finished/progress100 не доказывают завершение
авторизации или загрузки JS-приложения.
Лог устройства 2026-10-03 показал переход auth → login.php → login.vk.com → blank.html
с payload. Теперь первый payload с совпадающим state вызывает однократный повтор
исходного OAuth с сохранёнными cookies, без закрытия WebView. Повторный payload
передаётся обычному обработчику ошибки; цикл невозможен. Ввод кода/пароля и страницы
восстановления не являются триггером. Получение access_token после повтора ещё
не подтверждено на устройстве.
В следующем логе вместо callback наблюдался переход на
`https://id.vk.ru/account/#/main?account_action_redirect_url=…`.
Этот конкретный маршрут теперь также запускает однократный повтор OAuth
при изменении истории или завершении загрузки. Лимит общий с повтором после payload;
остальные страницы аккаунта и восстановления не являются триггером.
Повтор проверяет маршрут, но сам по себе не доказывает наличие авторизованной сессии;
поведение после возврата требует живой проверки.
Предлагаемый обход — повторить OAuth с включённой в браузере «Версией для ПК»;
на устройстве пользователя этот обход ещё не проверен. Нужен callback с access_token.

### Android WebView (2026-10-02)

`SettingsPlatform.hasEmbeddedVkLogin/VkLoginBrowser` отделяет платформенный UI от SDK.
Основная кнопка Android открывает Dialog на весь экран; Windows использует прежний
внешний браузер. WebView задаёт Windows desktop UA с фактической версией Chromium,
JavaScript, DOM storage, cookies и pinch zoom.
После сообщения об исчезающей форме кода (2026-10-03) широкий viewport и overview
отключены: desktop UA/Client Hints сохранены, но layout имеет ширину самого WebView.
Окно использует `decorFitsSystemWindows=true`; ручные systemBarsPadding/imePadding
убраны, чтобы не накладывать Compose-отступы на нативное изменение окна клавиатурой.
Это проверяемая правка геометрии, а не подтверждённая причина сбоя VK: нужен повтор
с переходом к коду, открытием/закрытием клавиатуры. `[layoutVkLogin]` сообщает только
размер окна, высоту контента и прокрутку, без содержимого формы и URL.
С 2026-10-03 Android подключает AndroidX WebKit 1.17.1 и до первой загрузки
через `WebSettingsCompat.setUserAgentMetadata` задаёт Client Hints: Windows,
mobile=false, пустую модель устройства, x86/64, Chromium/Google Chrome с фактической
версией из системного UA. `FORM_FACTOR_DESKTOP` включается отдельно при поддержке
`USER_AGENT_METADATA_FORM_FACTORS`. Старые WebView сохраняют подмену UA;
неподдерживаемые API не вызываются. `[configureVkDesktopMode]` сообщает поддержку
метаданных/form factor либо безопасный тип ошибки. Строка UA и Client Hints
настраиваются до `loadUrl`, повторный reload при создании не нужен.
Это экспериментальный способ получить обычный implicit callback, не гарантия
устранения silent_token: требуется живой тест с аккаунтом пользователя.

`shouldOverrideUrlLoading` перехватывает основной документ; `onPageStarted`,
`onPageFinished` и `doUpdateVisitedHistory` дополняют обработку редиректов/hash.
При доверенном HTTPS callback окно закрывается, SDK `parseAutomaticRedirect`
требует совпадение state, затем shared проверяет VK Music и сохраняет доступ.
Повторные события одного callback не запускают повторную авторизацию.

Над WebView одна панель высотой 48 dp с единственной кнопкой «Внешний браузер».
Закрытие — системной кнопкой «Назад». Заголовок, дополнительные панели, повтор
и накладки над страницей убраны 2026-10-03: они занимали место и мешали интерфейсу VK.
Ошибки загрузки и внешних переходов остаются в безопасной диагностике.
Внешние `intent://` и VK-схемы с основной страницы VK теперь запускаются через
Android Intent вместо безусловного запрета всего, кроме HTTPS. WebView остаётся
открытым; при отсутствии обработчика используется `browser_fallback_url`, если
это доверенный HTTPS-адрес VK. Диагностика `[openVkExternalLink]` сообщает схему,
пакет, наличие fallback и результат запуска без полного URI/экстра-данных.
Автоматическое возвращение результата из внешнего приложения не гарантировано:
в manifest/onNewIntent пока нет VK OAuth callback. Если внешнее приложение продолжит
ту же WebView-сессию, существующий перехват поймает callback; завершение во внешнем
браузере требует ручного сценария. Проверить оба пути на устройстве пользователя.
Во время загрузки маленький индикатор показан в той же верхней панели рядом с кнопкой.
Панель находится отдельной строкой над WebView и не перекрывает содержимое страницы.
Внешний fallback сохраняет state текущей операции; отдельная запасная кнопка
карточки начинает новый ручной вход. Отмена окна не меняет прежнюю авторизацию.
История WebView/callback не сериализуются; JS bridge отсутствует, console-вывод
страницы подавлен. Диагностика содержит этап, hostname, тип callback и числовой
код ошибки, без URL/query/fragment/профиля. SSL-ошибка отменяет соединение.
WebView уничтожается при закрытии; при пересоздании окна OAuth запускается заново
с сохранённым state. Cookies WebView могут сохраняться отдельно от внешнего браузера.

Проверить на Android: основной вход без копирования URL; отмену; fallback в браузер;
сетевую ошибку и повтор; смену аккаунта; пересоздание экрана. При повторном payload
в логах будет `[consumeVkRedirect] ... тип=payload VK ID` и snackbar с причиной.
Добавлена fixture-проверка строгого callback/state/origin; сборку и тесты агент не запускал.

Ошибка и результат входа выводятся в общий snackbar `SettingsRoute`, а также
контрастным текстом в начале карточки над полем. На нажатие «Завершить вход»
снимается фокус и скрывается клавиатура; ошибочное поле выделяется цветом.
Так сообщение не оказывается только под кнопками за пределами видимой прокрутки.
Добавлен синтетический тест payload с вложенными URL/`&` и проверкой state;
учётные данные пользователя не сохранены. Сборка и runtime-проверка правки не выполнялись.

Android хранит VK в отдельном зашифрованном SharedPreferences `vk_protected_session`,
исключённом из backup/transfer; Windows — отдельный DPAPI `vk-session.bin` рядом с
Яндекс-сессией. Удаление VK-входа не удаляет Яндекс-вход.

## Воспроизведение

`VkMusicRepository.play` индексирует выбранный трек через `SongRepository` и получает
постоянную Song с TrackInstance.Vk. Начальный Song/instance id — `vk:owner_id_audio_id`;
повторное обновление сохраняет существующую Song и ранее подтверждённые общие связи.
`playPlaylist` передаёт весь снимок VK-плейлиста и выбранный индекс в `PlayerRepository.playQueue`.
`VkPlaylistTracklist` сохраняет название и конечность списка; доступны обычные next/prev,
перемешивание и повтор. Порядок и повторяющиеся записи сохраняются. Завершение VK-плейлиста
не продолжает очередь Яндекс-волной.
В Room хранится source-метадата, а не адрес relay. MusicSource.VK сохраняется до платформенного плеера;
ни Яндекс-feedback, ни Яндекс-prefetch, ни Rotor по завершении не запускаются.

HLS URL переписывается relay, ключи и подписанные upstream URL остаются в памяти.
Android подключает media3-exoplayer-hls и разрешает cleartext только для 127.0.0.1;
JavaFX получает локальный m3u8 без AES-тегов, с MP3 вместо исходных TS-сегментов
(desktop-режим от 2026-10-05). Callback общей очереди создаёт
URI в действующем relay; переход к другому источнику отменяет активные чтения.
Смена аккаунта и завершение application scope закрывают relay и сбрасывают временные URI.
В одиночном сценарии и очередях прямой HTTPS-аудиофайл также проходит через relay.

Для полной очереди используется один relay: каждому треку заранее выдаётся локальный URI,
но запрос `audio.getById` остальных треков выполняется HTTP-worker только при открытии
их URI плеером. Выбранный трек также получает свежий URL лениво: сборка постоянной
Song не выполняет сетевой запрос. HEAD/GET одного открытия разделяют URL в течение 30 секунд; более позднее
открытие корня обновляет URL. Этот срок — локальная политика, не утверждение о времени
жизни ссылок VK. Корни HLS отдают переписанный m3u8, прямое аудио — bytes/range.

Обложки используют общий disk/memory cache с namespace vk-track, но независимую
загрузку HTTPS без Яндекс-прокси и преобразования URL.

## Диагностика и повторы VK (2026-10-02)

`VkHlsRelay.onDiagnostic` подключён к debug-журналу `VkMusicRepository`:
`[resolveVkAudio]` — получение ссылки/локального корня;
`[serveVkHls]` — ожидание worker, тип ресурса, этап, фактические байты и длительность;
`[fetchVkResource]` — числовой id, тип ресурса, host без пути/query, HTTP-статус,
ожидаемый размер и реально прочитанные байты. Ошибка отмечает последний этап
DNS/TCP/TLS/заголовки/тело. `[decodeVkMedia]` — AES-расшифровка.
Сообщения исключений, URI плеера, полные upstream URL и ключи не логируются.

Одновременные чтения одного ресурса/URL+range объединяются через FutureTask,
включая ожидание резолвера. Результаты отказов удаляются, новый GET может повторить загрузку.
`[joinVkResource]` показывает объединение. TCP connect ограничен 3с,
полный HLS HTTP-запрос — 20с (с 2026-10-09), отсутствие данных — также 20с;
прямой аудиофайл, читаемый целиком, сохраняет бюджет 25с.
Ленивый API-резолвер приложения ограничен 8с. Android разрешает до трёх повторов
загрузки Media3, но весь затык/подготовка ограничены общими 20с; затем snackbar
и переход к следующему треку без перезапуска текущей песни.
Загрузка целого bundle не имеет общего двадцатисекундного лимита: ограничен каждый сетевой ресурс.

Desktop подготовка VK ограничена 45с для последовательных API/master/media/segment/key;
stall — 20с для сегмента/ключа. Прежние 12с/5с остальных источников сохранены.
При смене трека/повторе desktop вызывает `cancelPendingPlaybackRequests` после закрытия JavaFX:
отменяются незавершённые FutureTask, API-резолверы через прерывание runBlocking, OkHttp calls
и старые loopback-соединения. Поколение запросов не даёт старому worker начать новый fetch.
Очередь, готовые сегменты и отдельные фоновые сохранения остаются рабочими.
`[cancelVkRequests]` и сообщение «отменён» отделяют штатный сброс от сетевого отказа.

Fixture-тесты `VkRelayRequestsTest` покрывают параллельные GET, отмену зависшего резолвера,
повтор того же корня после сброса, повтор после timeout и отсутствие секретов в ошибках.
Агент тесты/Gradle не запускает. После сборки проверить медленный VK-трек, next во время
подготовки, повтор после ошибки и сохранение плейлиста параллельно воспроизведению.

## Постоянный кеш аудио (2026-10-02)

`DwijComponent.start` подключает `VkAudioFileCache` к репозиторию. SDK использует
необязательный `VkAudioCache`, не зависящий от приложения. Файлы лежат в подкаталоге
`vk-audio` каталога кеша треков; каталог зарегистрирован в общем `CacheManager`.
Размер учитывается в настройках, общий лимит и удаление старых записей распространяются
на Яндекс, VK и обложки. Чтение обновляет время последнего использования.

Relay сохраняет полностью полученные, расшифрованные HLS-сегменты и init map конечного
плейлиста (`EXT-X-ENDLIST`); ключи AES и подписанные URL остаются в памяти.
Прямые аудиофайлы кешируются целиком: текущая реализация relay получает весь такой ресурс
перед отдачей плееру. HLS загружается отдельными сегментами по запросам плеера.
Кеш заполняется по мере чтения, без фонового скачивания всего плейлиста.

Ключ включает source-id и версию представления: пути ресурсов, тайминги, IV, ranges
и раскладку плейлиста. Параметры подписи (`extra`, `token`, `access_token`, `signature`,
`sig`, `sign`, `expires`, `exp`, `auth`) исключаются; неизвестные параметры, включая качество,
сохраняются. Изменившийся путь приводит к безопасной повторной загрузке.
Файлы содержат версию и SHA-256 готового аудио: повреждённая запись удаляется и загружается
повторно. Ошибка чтения/записи кеша не блокирует воспроизведение из сети.

Кеш переживает закрытие relay и перезапуск приложения. Сам обычный кеш не обеспечивает offline:
`audio.getById` и HLS-плейлисты запрашиваются заново, готовые сегменты берутся с диска.
Выход из аккаунта сбрасывает данные фонотеки в памяти, аудиокеш остаётся под общим LRU-лимитом.
Логи `[readVkAudioCache]` показывают попадания, `[writeVkAudioCache]` — запись без URL/токенов.
Добавлены fixture-тесты `VkAudioCacheTest` и `VkAudioFileCacheTest`: новый relay/экземпляр
хранилища, смена подписи, AES plaintext, разные треки/качество, ошибка диска, повреждение,
общий лимит. Агент их не запускал согласно AGENT.md.

После сборки: прослушать VK-трек, открыть его повторно, затем перезапустить приложение
и открыть снова. Проверить `[readVkAudioCache]`, seek/next, рост общего размера в настройках
и освобождение старых файлов при маленьком лимите. Повторить на Android и Windows.

## Плейлисты (2026-10-02)

Главная → источник «ВК Музыка» → «Плейлисты» открывает прежнюю общую сетку:

- Все страницы личных плейлистов через `users.get` и `audio.getPlaylists`.

- Открытие плитки: `audio.getPlaylistById` и полный состав через `audio.get`.
- «Создать»: прежний `CreatePlaylistDialog`, только название; `audio.createPlaylist`.
- Долгое нажатие на свой плейлист или меню открытого объекта: подтверждение и `audio.deletePlaylist`.
- Поиск → запустить VK-трек → «Добавить в плейлист» в плеере: выбор своего плейлиста и `audio.addToPlaylist`.
- Меню трека в плейлисте: «Добавить в плейлист» или подтверждённое «Удалить из плейлиста» (`audio.removeFromPlaylist`).

`navigation/VkPlaylistGridRoute.kt` использует общий `PlaylistGridContent`,
`navigation/VkPlaylistRoute.kt` — общий `ObjectScreen`. Платформенный код не дублируется.
Сетка и составы кешируются в Room отдельно для каждого аккаунта. При открытии
`VkPlaylistGridRoute` сразу показывает известную сетку, затем обновляет её в фоне.
Обновление не очищает составы и не загружает «Мои треки» для показа десяти плиток.
`VkPlaylistRoute` сначала читает `cachedPlaylist` без сетевого mutex, снимает loading
и показывает треки; затем пытается получить актуальный состав. Обложка загружается отдельно.
При сетевой ошибке уже показанный список остаётся доступен. Если кеша ещё нет,
первая загрузка по-прежнему требует сеть; пустой подтверждённый список считается кешем.
Offline-снимки остаются запасным источником данных без авторизации.

С 2026-10-06 состав открытого плейлиста, «Моих треков» и «Всех треков» удерживает
`models/VkPlaylistModel.kt`, привязанный к записи навигации через `viewModel`.
Загрузка работает в `viewModelScope`: переход в плеер её не отменяет, а обычный
возврат не запускает повторное чтение и не подменяет треки пустым списком/заглушками.
Общий `ObjectScreen` по-прежнему сохраняет индекс и смещение через `rememberLazyListState`;
при возврате он получает готовый состав из модели, необходимый для восстановления позиции.
Жест обновления и изменения коллекций (`membershipRevision`, включая добавление из плеера)
обновляют состав без очистки строк. Смена сессии/авторизации очищает прежний снимок;
отменённая загрузка не публикует результат поверх нового состояния.
Сетка уже хранит данные в репозитории и использует общий `rememberLazyGridState`.
`VkPlaylistGridModel` удерживает выбранное аудио и состояние загрузки на запись навигации:
возврат не повторяет запрос сетки или `getAudio`, смена сессии очищает выбранный трек.
Ручное обновление остаётся доступным. В режиме добавления членство догружается после
показа плиток; известные плейлисты подсвечиваются по source-ID/release-ID/серверным aliases.
Перед добавлением читается актуальный состав выбранного списка без offline-fallback;
если трек уже есть, предлагается подтверждение удаления именно найденного VK-экземпляра.
Не загруженный исходный трек вызывает сообщение вместо молчаливого игнорирования нажатия.
Обложки разрешаются по показанному набору плиток, включая `savedPlaylists` после выхода.

VK-строки наблюдают `SongRepository.vkSongs`: индикаторы нескольких источников и кандидатов
меняются вместе с общим индексом, без замены исходного порядка/дублей списка.
`play`/`playPlaylist` используют отдельный `queueMutex`, поэтому сборка очереди не ждёт
сетевого mutex обновления фонотеки. Индекс защищён собственным `vkIndexMutex`, доступ
к download-метадате — `ConcurrentHashMap`; перед передачей очереди проверяется ревизия сессии.
Это устраняет ожидание сетевой блокировки приложения, но не задержки сети самого аудио.
Проверка правки статическая; Gradle и runtime-проверка не выполнялись. На Android/desktop
проверить возврат из плеера после прокрутки каждого из трёх видов VK-треклистов,
возврат во время фоновой загрузки, обновление без сети, добавление/удаление из плеера,
индикаторы после объединения песен, обложки после выхода и запуск трека во время чтения составов.

Защищённый payload сессии VK теперь хранит JSON с token/accountId. Токен остаётся
в Android Keystore/Windows DPAPI. Прежний payload с одним токеном поддерживается:
после первого получения владельца сохраняется привязка аккаунта, далее перезапуск
восстанавливает его Room-кеш без сети. При выходе/смене аккаунта кеш в памяти сбрасывается;
снимок другого аккаунта не выбирается по принципу «последняя строка Room».
Сетка сохраняется без access_key, в том числе в original; перед первым сетевым
чтением состава после перезапуска перечитываются ключи из актуальной сетки VK.
Статус «Моих треков» из кеша используется для отображения, мутации требуют свежего состояния.

После добавления/удаления трека инвалидируется только изменённый состав;
после удаления плейлиста удаляется его кеш. `cachedPlaylist(VK_ALL_TRACKS)` доступен
только если известны «Мои треки» и составы всех списков сохранённой сетки.
`VkLibraryCacheTest` покрывает восстановление без сети, порядок с дублями,
изоляцию аккаунтов и пустые/неизвестные снимки. Тесты агентом не запускались.
Повторная отправка во время операции блокируется, ошибки показываются через snackbar
и логируются с контекстом метода и кодом VK, без токена или приватных URL.

Редактирование доступно своим плейлистам (`owner_id` текущего пользователя,
без `original`, с учётом `permissions.edit/delete`). Чужие сохранённые подборки
в этом сценарии только читаются; их состав получает owner/id/access_key из `original`.
Обложки плейлистов используют отдельный namespace `vk-playlist` общего кэша и транспорт VK.
Навигация плейлиста хранит составной owner/id, а ключ плейлиста берётся из личной сетки.

Нажатие на трек запускает полный список с выбранной позиции; кнопка воспроизведения — с первой.
Поиск сохраняет отдельный одиночный сценарий.

## Постоянное локальное хранение VK (2026-10-02)

Контекстное меню трека в поиске, VK-плейлисте и плеере содержит «Сохранить локально».
Меню заголовка плейлиста и долгое нажатие плитки сохраняют весь состав.
Снимок порядка, включая дубли, записывается отдельно; загрузочная очередь уникальна по source-id
и пропускает уже готовые/активно скачиваемые треки. При отказе одного трека остальные остаются
сохранёнными; на Android отказ авторизации останавливает очередь, как в прежнем сценарии.

`DwijComponent.saveTrackLocally` передаёт `vk:owner_id_audio_id` в VK-репозиторий,
другие id — в прежний `TrackCacheRepository`. Android использует тот же foreground-service
с уведомлением и прогрессом; Windows — application scope. Закрытие экрана не отменяет очередь.
Для HLS до конца графа показывается объём загруженного аудио с неизвестным total, затем итог.

`VkLocalStorage` хранит bundle в `vk-local-tracks` рядом с постоянным каталогом Яндекса
(Android noBackupFilesDir, Windows app-data). Этот каталог не зарегистрирован в CacheManager:
постоянные записи переживают LRU-очистку. Настройки считают размер Яндекс + VK и очищают оба.
Карточка постоянного хранения расположена сразу после карточки кеша: показывает общий
занятый объём и кнопку «Очистить». Кнопка открывает подтверждение; только согласие запускает
удаление постоянных файлов и VK-снимков. Во время очистки повторное подтверждение и закрытие
диалога недоступны. По завершении объём обновляется, результат показывается в snackbar.
Метадата трека содержит название, артистов, локальный корень и размеры всех ресурсов;
подписанный audio URL и access_key не сохраняются. Для текущей загрузочной сессии access_key
остаётся в памяти, не попадая в Intent, trackId, уведомление или журнал.

`VkHlsRelay.downloadAudio` сохраняет master/media playlists, init map и расшифрованные сегменты
с относительными именами; прямое аудио сохраняется целиком. Используются готовые записи обычного
кеша. Live/незавершённый HLS и оставшиеся неподдерживаемые внешние URI/ключи отклоняются.
Сначала пишется staging-каталог, после успеха — метадата и публикация каталога.
Сбой/отмена удаляют staging; после смерти процесса остатки удаляются при старте.
Bundle без всех ресурсов правильного размера не считается готовым.

Воспроизведение предпочитает постоянный bundle перед VK API. `openSavedAudio` отдаёт локальный
HLS через loopback с относительными ссылками, преобразованными в HTTP; интернет не используется.
Будущий трек уже созданной очереди также проверяет постоянный файл при открытии.
Если сохранение части плейлиста не удалось, готовые треки играют локально, остальные требуют сеть.

Сохранённые снимки восстанавливаются в VK-сетке после перезапуска и доступны без действующей
авторизации. Экран такого плейлиста сразу открывает снимок; «Обновить» читает серверный состав,
при отказе возвращается к сохранённому. Это снимок на момент сохранения, не автоматическая
синхронизация изменений VK. Поиск при отказе API возвращает совпадения в постоянно сохранённых
треках; сначала ожидается результат/таймаут API. Сохранение отдельного трека индексирует
метадату в Room, но не добавляет его в системную медиатеку или «Мои треки» VK.
Файлы остаются в app-private хранении и сохраняют источник VK.

Fixture-тесты `VkSavedAudioTest` проверяют master/AES-export, отсутствие URL/ключей, offline
новым relay, range, прямое аудио и запрет выхода из bundle. `VkLocalStorageTest` проверяет
перезапуск, снимок с дублями, неполные ресурсы и очистку. Тесты агентом не запускались.
Проверить после сборки: сохранить один трек и плейлист, дождаться окончания уведомления,
выключить сеть, перезапустить приложение, открыть сохранённый плейлист, проверить next/prev/seek.
Также проверить поиск сохранённого трека без сети, размеры/очистку в настройках и повторную
постановку частично загруженного плейлиста. Повторить на Android и Windows.
## Метки плейлистов в плеере

`FullPlayerUiState.canAddToPlaylist` отделён от `canLike`: VK показывает метки
и кнопку «Добавить в плейлист» без включения Яндекс-лайка или дизлайка.
`PlayerRoute` выбирает VK-инстанс по реально играющему source-id и берёт метки из
`VkMusicRepository.playlistTracks`. Плейлист запуска известен сразу; недостающие составы
личных плейлистов загружаются в фоне и кэшируются в памяти текущей сессии.
При смене трека успешно загруженные составы не запрашиваются заново.
После добавления/удаления инвалидируется состав изменённого плейлиста;
создание/удаление обновляет список, смена аккаунта очищает снимки фонотеки в памяти.
Составы из Room показываются сразу; после перезапуска плеер подтверждает их в фоне
один раз за сессию. Обновление конкретного плейлиста перечитывает внешние изменения,
а обновление сетки больше не сбрасывает весь кеш составов.
Первый полный обход большой фонотеки может занять время; кнопка добавления доступна сразу.

## Личная коллекция и общая фонотека

- В обычной сетке VK сначала **«Создать плейлист»**, затем **«Мои треки»**. Это виртуальный список `0_-1`,
  получаемый через полный обход `audio.get(owner_id)` без `album_id`.
- Лайк в плеере VK и действия в меню трека добавляют/удаляют запись в этой коллекции.
  Дизлайк Яндекс-волны для VK не показывается. Добавление в плейлист по-прежнему
  вызывает отдельный `audio.addToPlaylist` и не меняет статус личной коллекции.
- **«Треки»** на главной открывает виртуальный список `0_-2`: «Мои треки», затем
  состав каждого плейлиста из `audio.getPlaylists`, включая сохранённые чужие подборки.
  Каждая коллекция читается полностью с пагинацией; отказ одного плейлиста показывается
  ошибкой, а не частичным «полным» результатом. Первый обход большой фонотеки может быть долгим.
- Объединение сохраняет первое вхождение и убирает повторные source-id, серверные
  `release_audio_id` и известные связи `audio.add`. Треки не объединяются по названию.
  Если VK выдаёт разные ID без связи с релизом, неизвестные копии остаются отдельными записями.
- `audio.add` может вернуть новый owner/id в `items[].new_owner_id/new_audio_id`.
  Удаление использует личный экземпляр; связь с исходным ID хранится по аккаунтам
  в аккаунтном снимке Room и переживает рестарт; прежний файл VK local storage читается
  только как источник импорта, если снимка Room ещё нет. `like` из сырой метадаты не используется
  как подтверждение членства; лайк доступен после загрузки коллекции.
- Виртуальные списки используют общий экран и полную очередь VK, доступны для
  постоянного сохранения через меню шапки. Они не удаляются как серверные плейлисты
  и не входят в селектор добавления в плейлист. Сохранённый снимок открывается при отказе VK;
  онлайн-открытие виртуального списка всегда пытается получить свежий состав.

После сборки проверить: создание первым, «Мои треки» вторыми в сетке; лайк и снятие лайка в плеере
и меню; добавление в обычный плейлист без лайка; общий список с пересечениями двух
плейлистов; запуск с середины и next/prev; повторный лайк после рестарта; переключение
аккаунта и сетевую ошибку. Код общий для Android/Windows; сборку и runtime-проверку
новой коллекции агент не запускал. Добавлены fixture-тесты `VkCollectionTest`,
`VkLibraryTracksTest` и проверка аккаунтного хранения связей в `VkLocalStorageTest`.
