# ВК Музыка: поиск и плейлисты

## Подключение

`vkMusicSdk/` — независимый Kotlin/JVM SDK (Android и desktop, JVM 11).
Он не зависит от shared, Android, JavaFX или yaMusicSdk. Shared подключает его через
`api(project(":vkMusicSdk"))`; оба приложения получают его через shared.
SDK теперь отдельный Git-репозиторий, подключённый субмодулем. Изменения SDK
коммитятся и публикуются в нём, затем обновляется указатель в репозитории Движа.

- `VkApiClient`: token-based POST, отмена HTTP вместе с coroutine, версия 5.282;
  audio.search, getSearchSuggestions, catalog.getAudio/getSection, audio.add/delete.
- Дополнения по vkpymusic: audio.getById, пагинация плейлистов/треков,
  рекомендации. Каталог пока доступен сырым JsonElement; UI каталога VK не реализован.
- `VkOAuth`: OAuth Маруси из README LavaSrc, без клиентского секрета и cookies.
- `VkHlsRelay`: ограниченный текущим воспроизведением loopback-сервер для VOD HLS;
  relative URI, master playlist, AES-128, смена ключей, sequence/explicit IV,
  MAP и BYTERANGE. Нет перекодирования; поддержка контейнера зависит от плеера.

## Вход и поиск

1. Настройки → ВК Музыка → «Войти в VK через Марусю».
2. Android открывает собственный полноэкранный WebView с desktop User-Agent;
   после входа callback перехватывается автоматически. Windows открывает внешний браузер.
3. Во внешнем браузере скопировать полный URL страницы `oauth.vk.com/blank.html`
   (или oauth.vk.ru), вернуться в приложение, вставить URL, нажать «Завершить вход».
4. Callback проверяется по HTTPS origin/path (oauth.vk.com или oauth.vk.ru) и совпадению state,
   если он присутствует. Автоматический callback требует state; только при явной ручной
   вставке отсутствие state допустимо (формат из LavaSrc).
   До сохранения выполняется
   audio.search с полученным токеном. Ошибка не заменяет прежнюю сессию.
5. Главная → Поиск → источник «ВК Музыка» → запрос → нажатие на трек.

На Android `AndroidVkLoginBrowser` реализует автоматический callback через WebView;
внешний браузер остаётся запасным ручным сценарием, автоматического deep link нет.
OAuth state переживает пересоздание экрана;
URL с токеном не сохраняется в saved state. Токен не выводится в логи.
Поле показывает ссылку обычным многострочным текстом (3–6 строк) с переносом длинного URL.
Цвета кнопок, отключённых состояний и label заданы явно для тёмной карточки.
Разбор отклонённого адреса возвращает конкретную причину: неверный URL/origin,
нет части после #, нет токена, повреждённые параметры, отказ VK или несовпадающий state.
Логи `[completeVkAuthorization]` сообщают эту причину либо факт принятия ссылки
и наличие/совпадение state; сам URL, токен и OAuth error_description не логируются.

Android-проверка 2026-10-02 выявила другой ответ VK: `#payload=...&state=...`,
внутри payload `type=silent_token`, `ttl=600`, вместо `access_token`.
Этот промежуточный ответ VK ID пока не поддерживается для входа в музыку:
SDK возвращает отдельную причину `VkIdPayload`, не принимает payload.token как access_token
и не отправляет его в audio.search. Автоматический обмен silent_token не реализован.
Предлагаемый обход — повторить OAuth с включённой в браузере «Версией для ПК»;
на устройстве пользователя этот обход ещё не проверен. Нужен callback с access_token.

### Android WebView (2026-10-02)

`SettingsPlatform.hasEmbeddedVkLogin/VkLoginBrowser` отделяет платформенный UI от SDK.
Основная кнопка Android открывает Dialog на весь экран; Windows использует прежний
внешний браузер. WebView задаёт Windows desktop UA с фактической версией Chromium,
JavaScript, DOM storage, cookies, широкий viewport, обзорный масштаб и pinch zoom.
Это экспериментальный способ получить обычный implicit callback, не гарантия
устранения silent_token: требуется живой тест с аккаунтом пользователя.

`shouldOverrideUrlLoading` перехватывает основной документ; `onPageStarted`,
`onPageFinished` и `doUpdateVisitedHistory` дополняют обработку редиректов/hash.
При доверенном HTTPS callback окно закрывается, SDK `parseAutomaticRedirect`
требует совпадение state, затем shared проверяет VK Music и сохраняет доступ.
Повторные события одного callback не запускают повторную авторизацию.

В WebView есть «Закрыть», «Открыть в браузере» и повтор загрузки после ошибки.
Внешние `intent://` и VK-схемы с основной страницы VK теперь запускаются через
Android Intent вместо безусловного запрета всего, кроме HTTPS. WebView остаётся
открытым; при отсутствии обработчика используется `browser_fallback_url`, если
это доверенный HTTPS-адрес VK. Диагностика `[openVkExternalLink]` сообщает схему,
пакет, наличие fallback и результат запуска без полного URI/экстра-данных.
Автоматическое возвращение результата из внешнего приложения не гарантировано:
в manifest/onNewIntent пока нет VK OAuth callback. Если внешнее приложение продолжит
ту же WebView-сессию, существующий перехват поймает callback; завершение во внешнем
браузере требует ручного сценария. Проверить оба пути на устройстве пользователя.
Во время загрузки над WebView показаны центральный индикатор и «Загружаем страницу
входа VK…». После восьми секунд появляется подсказка о долгом ответе VK; ожидание
не обрывается, кнопки закрытия и внешнего браузера остаются доступными.
Внешний fallback сохраняет state текущей операции; отдельная запасная кнопка
карточки начинает новый ручной вход. Отмена окна не меняет прежнюю авторизацию.
История WebView/callback не сериализуются; JS bridge отсутствует, console-вывод
страницы подавлен. Диагностика содержит этап, hostname, тип callback и числовой
код ошибки, без URL/query/fragment/профиля. SSL-ошибка отменяет соединение.
WebView уничтожается при закрытии; при пересоздании окна OAuth запускается заново
с сохранённым state. Cookies WebView могут сохраняться отдельно от внешнего браузера.

Проверить на Android: основной вход без копирования URL; отмену; fallback в браузер;
сетевую ошибку и повтор; смену аккаунта; пересоздание экрана. При повторном payload
в логах будет `[consumeVkRedirect] ... тип=payload VK ID` и snackbar с причиной.
Добавлена fixture-проверка строгого callback/state/origin; сборку и тесты агент не запускал.

Ошибка и результат входа выводятся в общий snackbar `SettingsRoute`, а также
контрастным текстом в начале карточки над полем. На нажатие «Завершить вход»
снимается фокус и скрывается клавиатура; ошибочное поле выделяется цветом.
Так сообщение не оказывается только под кнопками за пределами видимой прокрутки.
Добавлен синтетический тест payload с вложенными URL/`&` и проверкой state;
учётные данные пользователя не сохранены. Сборка и runtime-проверка правки не выполнялись.

Android хранит VK в отдельном зашифрованном SharedPreferences `vk_protected_session`,
исключённом из backup/transfer; Windows — отдельный DPAPI `vk-session.bin` рядом с
Яндекс-сессией. Удаление VK-входа не удаляет Яндекс-вход.

## Воспроизведение

`VkMusicRepository.play` запрашивает свежий URL через audio.getById и создаёт
временный Song с TrackInstance.Vk и составным id `vk:owner_id_audio_id`.
`playPlaylist` передаёт весь снимок VK-плейлиста и выбранный индекс в `PlayerRepository.playQueue`.
`VkPlaylistTracklist` сохраняет название и конечность списка; доступны обычные next/prev,
перемешивание и повтор. Порядок и повторяющиеся записи сохраняются. Завершение VK-плейлиста
не продолжает очередь Яндекс-волной.
В Room трек не записывается. MusicSource.VK сохраняется до платформенного плеера;
ни Яндекс-feedback, ни Яндекс-prefetch, ни Rotor по завершении не запускаются.

HLS URL переписывается relay, ключи и подписанные upstream URL остаются в памяти.
Android подключает media3-exoplayer-hls и разрешает cleartext только для 127.0.0.1;
JavaFX получает обычный локальный m3u8 без AES-тегов. Новый выбор заменяет relay
после передачи очереди плееру; переход к другому источнику и завершение application scope закрывают ресурсы.
В одиночном сценарии и очередях прямой HTTPS-аудиофайл также проходит через relay.

Для полной очереди используется один relay: каждому треку заранее выдаётся локальный URI,
но запрос `audio.getById` остальных треков выполняется HTTP-worker только при открытии
их URI плеером. Выбранный трек проверяется до передачи очереди; его свежий URL передаётся
как seed. HEAD/GET одного открытия разделяют URL в течение 30 секунд; более позднее
открытие корня обновляет URL. Этот срок — локальная политика, не утверждение о времени
жизни ссылок VK. Корни HLS отдают переписанный m3u8, прямое аудио — bytes/range.

Обложки используют общий disk/memory cache с namespace vk-track, но независимую
загрузку HTTPS без Яндекс-прокси и преобразования URL.

## Диагностика и повторы VK (2026-10-02)

`VkHlsRelay.onDiagnostic` подключён к debug-журналу `VkMusicRepository`:
`[resolveVkAudio]` — получение ссылки/локального корня;
`[serveVkHls]` — ожидание worker, тип ресурса, этап, фактические байты и длительность;
`[fetchVkResource]` — числовой id, тип ресурса, host без пути/query, HTTP-статус,
ожидаемый размер и реально прочитанные байты. Ошибка отмечает последний этап
DNS/TCP/TLS/заголовки/тело. `[decodeVkMedia]` — AES-расшифровка.
Сообщения исключений, URI плеера, полные upstream URL и ключи не логируются.

Одновременные чтения одного ресурса/URL+range объединяются через FutureTask,
включая ожидание резолвера. Результаты отказов удаляются, новый GET может повторить загрузку.
`[joinVkResource]` показывает объединение. TCP connect ограничен 3с, отсутствие данных — 5с,
полный HLS HTTP-запрос — 8с; прямой аудиофайл, читаемый целиком, сохраняет бюджет 25с.
Ленивый API-резолвер приложения ограничен 8с.
Загрузка целого bundle не имеет общего 8-секундного лимита: ограничен каждый сетевой ресурс.

Desktop подготовка VK ограничена 45с для последовательных API/master/media/segment/key;
stall — 20с для сегмента/ключа. Прежние 12с/5с остальных источников сохранены.
При смене трека/повторе desktop вызывает `cancelPendingPlaybackRequests` после закрытия JavaFX:
отменяются незавершённые FutureTask, API-резолверы через прерывание runBlocking, OkHttp calls
и старые loopback-соединения. Поколение запросов не даёт старому worker начать новый fetch.
Очередь, готовые сегменты и отдельные фоновые сохранения остаются рабочими.
`[cancelVkRequests]` и сообщение «отменён» отделяют штатный сброс от сетевого отказа.

Fixture-тесты `VkRelayRequestsTest` покрывают параллельные GET, отмену зависшего резолвера,
повтор того же корня после сброса, повтор после timeout и отсутствие секретов в ошибках.
Агент тесты/Gradle не запускает. После сборки проверить медленный VK-трек, next во время
подготовки, повтор после ошибки и сохранение плейлиста параллельно воспроизведению.

## Постоянный кеш аудио (2026-10-02)

`DwijComponent.start` подключает `VkAudioFileCache` к репозиторию. SDK использует
необязательный `VkAudioCache`, не зависящий от приложения. Файлы лежат в подкаталоге
`vk-audio` каталога кеша треков; каталог зарегистрирован в общем `CacheManager`.
Размер учитывается в настройках, общий лимит и удаление старых записей распространяются
на Яндекс, VK и обложки. Чтение обновляет время последнего использования.

Relay сохраняет полностью полученные, расшифрованные HLS-сегменты и init map конечного
плейлиста (`EXT-X-ENDLIST`); ключи AES и подписанные URL остаются в памяти.
Прямые аудиофайлы кешируются целиком: текущая реализация relay получает весь такой ресурс
перед отдачей плееру. HLS загружается отдельными сегментами по запросам плеера.
Кеш заполняется по мере чтения, без фонового скачивания всего плейлиста.

Ключ включает source-id и версию представления: пути ресурсов, тайминги, IV, ranges
и раскладку плейлиста. Параметры подписи (`extra`, `token`, `access_token`, `signature`,
`sig`, `sign`, `expires`, `exp`, `auth`) исключаются; неизвестные параметры, включая качество,
сохраняются. Изменившийся путь приводит к безопасной повторной загрузке.
Файлы содержат версию и SHA-256 готового аудио: повреждённая запись удаляется и загружается
повторно. Ошибка чтения/записи кеша не блокирует воспроизведение из сети.

Кеш переживает закрытие relay и перезапуск приложения. Сам обычный кеш не обеспечивает offline:
`audio.getById` и HLS-плейлисты запрашиваются заново, готовые сегменты берутся с диска.
Выход из аккаунта сбрасывает данные фонотеки в памяти, аудиокеш остаётся под общим LRU-лимитом.
Логи `[readVkAudioCache]` показывают попадания, `[writeVkAudioCache]` — запись без URL/токенов.
Добавлены fixture-тесты `VkAudioCacheTest` и `VkAudioFileCacheTest`: новый relay/экземпляр
хранилища, смена подписи, AES plaintext, разные треки/качество, ошибка диска, повреждение,
общий лимит. Агент их не запускал согласно AGENT.md.

После сборки: прослушать VK-трек, открыть его повторно, затем перезапустить приложение
и открыть снова. Проверить `[readVkAudioCache]`, seek/next, рост общего размера в настройках
и освобождение старых файлов при маленьком лимите. Повторить на Android и Windows.

## Плейлисты (2026-10-02)

Главная → источник «ВК Музыка» → «Плейлисты» открывает прежнюю общую сетку:

- Все страницы личных плейлистов через `users.get` и `audio.getPlaylists`.

- Открытие плитки: `audio.getPlaylistById` и полный состав через `audio.get`.
- «Создать»: прежний `CreatePlaylistDialog`, только название; `audio.createPlaylist`.
- Долгое нажатие на свой плейлист или меню открытого объекта: подтверждение и `audio.deletePlaylist`.
- Поиск → запустить VK-трек → «Добавить в плейлист» в плеере: выбор своего плейлиста и `audio.addToPlaylist`.
- Меню трека в плейлисте: «Добавить в плейлист» или подтверждённое «Удалить из плейлиста» (`audio.removeFromPlaylist`).

`navigation/VkPlaylistGridRoute.kt` использует общий `PlaylistGridContent`,
`navigation/VkPlaylistRoute.kt` — общий `ObjectScreen`. Платформенный код не дублируется.
`VkMusicRepository` хранит список и id аккаунта в памяти текущей сессии;
после выхода/смены аккаунта они сбрасываются. Список и состав перечитываются
при открытии и обновлении. После удаления трека перечитывается актуальный состав.
Повторная отправка во время операции блокируется, ошибки показываются через snackbar
и логируются с контекстом метода и кодом VK, без токена или приватных URL.

Редактирование доступно своим плейлистам (`owner_id` текущего пользователя,
без `original`, с учётом `permissions.edit/delete`). Чужие сохранённые подборки
в этом сценарии только читаются; их состав получает owner/id/access_key из `original`.
Обложки плейлистов используют отдельный namespace `vk-playlist` общего кэша и транспорт VK.
Навигация плейлиста хранит составной owner/id, а ключ плейлиста берётся из личной сетки.

Нажатие на трек запускает полный список с выбранной позиции; кнопка воспроизведения — с первой.
Поиск сохраняет отдельный одиночный сценарий.

## Постоянное локальное хранение VK (2026-10-02)

Контекстное меню трека в поиске, VK-плейлисте и плеере содержит «Сохранить локально».
Меню заголовка плейлиста и долгое нажатие плитки сохраняют весь состав.
Снимок порядка, включая дубли, записывается отдельно; загрузочная очередь уникальна по source-id
и пропускает уже готовые/активно скачиваемые треки. При отказе одного трека остальные остаются
сохранёнными; на Android отказ авторизации останавливает очередь, как в прежнем сценарии.

`DwijComponent.saveTrackLocally` передаёт `vk:owner_id_audio_id` в VK-репозиторий,
другие id — в прежний `TrackCacheRepository`. Android использует тот же foreground-service
с уведомлением и прогрессом; Windows — application scope. Закрытие экрана не отменяет очередь.
Для HLS до конца графа показывается объём загруженного аудио с неизвестным total, затем итог.

`VkLocalStorage` хранит bundle в `vk-local-tracks` рядом с постоянным каталогом Яндекса
(Android noBackupFilesDir, Windows app-data). Этот каталог не зарегистрирован в CacheManager:
постоянные записи переживают LRU-очистку. Настройки считают размер Яндекс + VK и очищают оба.
Метадата трека содержит название, артистов, локальный корень и размеры всех ресурсов;
подписанный audio URL и access_key не сохраняются. Для текущей загрузочной сессии access_key
остаётся в памяти, не попадая в Intent, trackId, уведомление или журнал.

`VkHlsRelay.downloadAudio` сохраняет master/media playlists, init map и расшифрованные сегменты
с относительными именами; прямое аудио сохраняется целиком. Используются готовые записи обычного
кеша. Live/незавершённый HLS и оставшиеся неподдерживаемые внешние URI/ключи отклоняются.
Сначала пишется staging-каталог, после успеха — метадата и публикация каталога.
Сбой/отмена удаляют staging; после смерти процесса остатки удаляются при старте.
Bundle без всех ресурсов правильного размера не считается готовым.

Воспроизведение предпочитает постоянный bundle перед VK API. `openSavedAudio` отдаёт локальный
HLS через loopback с относительными ссылками, преобразованными в HTTP; интернет не используется.
Будущий трек уже созданной очереди также проверяет постоянный файл при открытии.
Если сохранение части плейлиста не удалось, готовые треки играют локально, остальные требуют сеть.

Сохранённые снимки восстанавливаются в VK-сетке после перезапуска и доступны без действующей
авторизации. Экран такого плейлиста сразу открывает снимок; «Обновить» читает серверный состав,
при отказе возвращается к сохранённому. Это снимок на момент сохранения, не автоматическая
синхронизация изменений VK. Поиск при отказе API возвращает совпадения в постоянно сохранённых
треках; сначала ожидается результат/таймаут API. Сохранение отдельного трека не добавляет его
в Room или системную локальную медиатеку — как постоянные Яндекс-файлы, это app-private хранение.

Fixture-тесты `VkSavedAudioTest` проверяют master/AES-export, отсутствие URL/ключей, offline
новым relay, range, прямое аудио и запрет выхода из bundle. `VkLocalStorageTest` проверяет
перезапуск, снимок с дублями, неполные ресурсы и очистку. Тесты агентом не запускались.
Проверить после сборки: сохранить один трек и плейлист, дождаться окончания уведомления,
выключить сеть, перезапустить приложение, открыть сохранённый плейлист, проверить next/prev/seek.
Также проверить поиск сохранённого трека без сети, размеры/очистку в настройках и повторную
постановку частично загруженного плейлиста. Повторить на Android и Windows.
## Метки плейлистов в плеере

`FullPlayerUiState.canAddToPlaylist` отделён от `canLike`: VK показывает метки
и кнопку «Добавить в плейлист» без включения Яндекс-лайка или дизлайка.
`PlayerRoute` выбирает VK-инстанс по реально играющему source-id и берёт метки из
`VkMusicRepository.playlistTracks`. Плейлист запуска известен сразу; недостающие составы
личных плейлистов загружаются в фоне и кэшируются в памяти текущей сессии.
При смене трека успешно загруженные составы не запрашиваются заново.
После добавления/удаления инвалидируется состав изменённого плейлиста;
создание/удаление обновляет список, смена аккаунта очищает снимки фонотеки в памяти. Обновление сетки
сбрасывает снимки состава, позволяя перечитать изменения, сделанные во внешнем VK.
Первый полный обход большой фонотеки может занять время; кнопка добавления доступна сразу.

## Личная коллекция и общая фонотека

- В обычной сетке VK сначала **«Создать плейлист»**, затем **«Мои треки»**. Это виртуальный список `0_-1`,
  получаемый через полный обход `audio.get(owner_id)` без `album_id`.
- Лайк в плеере VK и действия в меню трека добавляют/удаляют запись в этой коллекции.
  Дизлайк Яндекс-волны для VK не показывается. Добавление в плейлист по-прежнему
  вызывает отдельный `audio.addToPlaylist` и не меняет статус личной коллекции.
- **«Треки»** на главной открывает виртуальный список `0_-2`: «Мои треки», затем
  состав каждого плейлиста из `audio.getPlaylists`, включая сохранённые чужие подборки.
  Каждая коллекция читается полностью с пагинацией; отказ одного плейлиста показывается
  ошибкой, а не частичным «полным» результатом. Первый обход большой фонотеки может быть долгим.
- Объединение сохраняет первое вхождение и убирает повторные source-id, серверные
  `release_audio_id` и известные связи `audio.add`. Треки не объединяются по названию.
  Если VK выдаёт разные ID без связи с релизом, неизвестные копии остаются отдельными записями.
- `audio.add` может вернуть новый owner/id в `items[].new_owner_id/new_audio_id`.
  Удаление использует личный экземпляр; связь с исходным ID хранится по аккаунтам
  в VK local storage и переживает рестарт. `like` из сырой метадаты не используется
  как подтверждение членства; лайк доступен после загрузки коллекции.
- Виртуальные списки используют общий экран и полную очередь VK, доступны для
  постоянного сохранения через меню шапки. Они не удаляются как серверные плейлисты
  и не входят в селектор добавления в плейлист. Сохранённый снимок открывается при отказе VK;
  онлайн-открытие виртуального списка всегда пытается получить свежий состав.

После сборки проверить: создание первым, «Мои треки» вторыми в сетке; лайк и снятие лайка в плеере
и меню; добавление в обычный плейлист без лайка; общий список с пересечениями двух
плейлистов; запуск с середины и next/prev; повторный лайк после рестарта; переключение
аккаунта и сетевую ошибку. Код общий для Android/Windows; сборку и runtime-проверку
