# Возобновление Android-плеера после потери Bluetooth

- `ExoPlayer.setHandleAudioBecomingNoisy(true)` ставит воспроизведение на паузу при исчезновении аудиовыхода. Подключение выхода обратно само по себе не вызывает `play()`. Причину паузы можно различить в `Player.Listener.onPlayWhenReadyChanged` по `PLAY_WHEN_READY_CHANGE_REASON_AUDIO_BECOMING_NOISY`.
- `BluetoothPlaybackResume` действует, пока жив `PlayerService`: запоминает прежний Bluetooth-аудиовыход и продолжает воспроизведение только при его возвращении. Ручная пауза сбрасывает ожидание. На Android 26–27, а также если аудиовыход не сообщает адрес, идентичность определяется типом и именем устройства; при нескольких Bluetooth-выходах автопродолжение не выполняется.
- Media3 может остановить `MediaSessionService` после длительной паузы. `PlaybackResumeStore` сохраняет URI очереди, нужные метаданные и позицию в `SharedPreferences`. `MediaButtonReceiver` и `MediaSession.Callback.onPlaybackResumption()` дают возможность возобновить воспроизведение кнопкой гарнитуры или системной панелью после пересоздания сервиса и процесса.
- Восстановление Media3 само по себе не заполняет общую UI-очередь. `PlayerService.publishQueue()` публикует фактическую timeline в `AndroidPlayerEngine` и через `AndroidPlaybackQueueRestorer` восстанавливает пустой `PlayerRepository`: локальная БД читается на IO, источник определяется по сохранённым extras, URI и порядок берутся из плеера. Если песня отсутствует в БД, используется сохранённая метадата без удаления позиции из очереди. Старые снимки без ID логической песни/экземпляра поддерживаются по source-ID.
- Изменение timeline отменяет устаревшую загрузку; принятие очереди не вызывает `setQueue`, `prepare`, `play` или `seek`. Непустая пользовательская очередь имеет приоритет. `AndroidPlayerEngine` сохраняет полученную очередь для последующего пересоздания сервиса; снимок из памяти не заменяет уже заполненный плеер.
- Исходный контекст треклиста (название плейлиста, seed волны) прежний `PlaybackResumeStore` не сохранял: после смерти процесса UI показывает «Текущая очередь», автоматическое продолжение ЯМ-волной не восстанавливается. Это ограничение не меняется при синхронизации UI. На устройстве следует проверить: завершение процесса → внешняя Play → открытие приложения, переход вперёд/назад, перемотку, shuffle/repeat и выбор новой очереди во время восстановления.
- Само подключение Bluetooth после смерти процесса не гарантирует автоматический запуск: Android ограничивает запуск foreground service из фонового Bluetooth-broadcast. Для такого сценария потребовалась бы отдельная модель доступа к companion-устройству и проверка на целевых версиях Android. Не следует подменять это отправкой искусственной медиакнопки из фонового receiver.

Источники: [ExoPlayer и noisy](https://developer.android.com/reference/androidx/media3/exoplayer/ExoPlayer#setHandleAudioBecomingNoisy(boolean)), [Media3 playback resumption](https://developer.android.com/media/media3/session/background-playback), [ограничения запуска foreground service](https://developer.android.com/develop/background-work/services/fgs/restrictions-bg-start).
