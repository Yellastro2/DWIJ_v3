# Потоковое воспроизведение ЯМ

Android использует `YaLazyDataSourceFactory`: готовый постоянный файл или полный
кэш открывается обычным Media3 DataSource. Для отсутствующего трека используется
`StreamingTrackCache` из `shared/.../playback/stream`.

## Загрузка и перемотка

На один trackId создаётся одна `StreamingTrackSession`. SDK получает прямую
ссылку стандартным download-info механизмом. `YamApiClient.audioRange` выполняет
отменяемые HTTP-запросы через текущие клиенты `YamConnectionFactory`, поэтому
сохраняются HTTP/SOCKS-прокси ЯМ. OAuth на аудиосервер не передаётся.

Запросы ограничены 256 КиБ; внутри ответа данные записываются и становятся
доступны плееру порциями до 32 КиБ. Полного ответа перед началом чтения ждать
не нужно. Одновременно выполняется один запрос на сессию. После текущего
диапазона приоритет получает позиция, которую запросил Media3. Затем загрузчик
заполняет оставшиеся пробелы. При медленной сети seek может ждать окончания
текущего диапазона или сетевого таймаута.

Ответ 206 проверяется по Content-Range, Content-Length, общему размеру и ETag.
При ответе 200 данные всегда записываются с нулевой позиции: сервер, который
игнорирует Range, приводит к последовательной загрузке и более долгому seek.
Неизвестный общий размер отклоняется. Ссылку фиксируем на сессию; автоматически
подменять её с сохранением диапазонов нельзя без проверки идентичности аудио.
Изменившиеся размер/ETag приводят к ошибке и удалению временных данных.
Временный сетевой сбой повторяется один раз на том же диапазоне.

## Диагностика загрузки

`TrackStream [resolveUrl]` связывает ID трека с хостом аудио; `[rangeFailed]`
показывает смещение, номер попытки, длительность и категорию ошибки.
`YamNetwork [networkStart]` назначает сетевому вызову ID и показывает хост и Range.
По тому же ID `[networkHeaders]` показывает HTTP-статус, `[networkBody]` —
число прочитанных байтов, `[networkConnectFailed]` и `[networkFailed]` —
последний этап (DNS, TCP/прокси, TLS, заголовки, тело), время, адрес сокета,
тип прокси и классы исключения/причины. Для SOCKS разрешение адреса может
выполняться внутри подключения, без отдельного DNS-события OkHttp.
Полные URL, их пути и query, авторизация и сообщения исключений в этих
диагностических событиях не выводятся. Чтение тела не гарантирует получение
первого байта; при сбое количество фактически переданных в кэш байтов видно
по логам потока. Закрытие тела не означает успешную проверку аудиодиапазона.

`DesktopAudioRelay [timeout]` показывает этап и отправленные байты:
ожидание длины/кэша означает ожидание источника, отправка JavaFX — ожидание
локального потребителя.

## Таймауты и повторы desktop

SDK использует по умолчанию 3с на подключение и 5с без новых сетевых данных
(эти значения общие для клиентов YamHttpTransport, включая Android).
Диапазон по-прежнему повторяется один раз через 250мс.
DesktopPlayerEngine ограничивает подготовку до READY 12 секундами на попытку,
включая получение ссылки и внутренние повторы JavaFX. После отказа старый
плеер освобождается, источник сбрасывается и через 250мс начинается новая
попытка всей цепочки. Разрешены первая попытка и три повтора; после четвёртого
отказа включается следующий трек по текущему порядку очереди без диалога.
Если следующего трека нет (или repeat-all возвращает тот же единственный трек),
воспроизведение останавливается. Четыре полных таймаута занимают около 49с.
Ручная смена трека и закрытие делают запоздалые сигналы старой попытки неактуальными.
STALLED во время запрошенного воспроизведения допускается до 5с, затем применяется
та же политика восстановления. Возврат в PLAYING или пауза отменяет этот таймер.
Watchdog relay ограничивает ожидание источника 12с, но не закрывает запрос
только потому, что JavaFX перестал читать уже доступное аудио. Такие запросы
закрываются при смене трека, сбросе источника или закрытии приложения.

## Таймауты и повторы Android

`AndroidPlaybackRecovery` в `PlayerService` применяет тот же бюджет:
12с до READY, 5с BUFFERING после готовности при playWhenReady, первая попытка
и три повтора всей цепочки через 250мс. Встроенные повторы загрузки Media3
отключены через `AndroidPlaybackLoadErrorPolicy`; один повтор диапазона в
общем загрузчике остаётся. Сетевые 3с/5с уже заданы общим SDK.

Перед повтором вызываются stop, сброс потокового источника, seek к началу
и prepare. Готовый кэш остаётся доступным. После четвёртого отказа плеер
переходит дальше с учётом shuffle/repeat-all; repeat-one не удерживает
неисправный трек. При отсутствии следующего элемента очередь останавливается
с TrackListEnd, без ShowError или кнопок. Пауза сохраняется при восстановлении.

Ручной выбор, смена очереди, перемотка и уничтожение сервиса отменяют старые
задачи. Обновление обложки и повторные BUFFERING не сбрасывают дедлайн/счётчик.
Логи `[retryTrack]` содержат трек, индекс, попытку и причину; `[skipFailedTrack]`
показывает окончательный пропуск. Проверка на устройстве после сборки:
недоступное аудио, успешный повтор, смена трека во время retry, пауза при
буферизации, shuffle и отказ последнего/единственного элемента очереди.

## Целостность и жизненный цикл

- В `cache/tracks/inflight` (подкаталог фактического trackCacheDirectory)
  находятся только временные `.part` активных загрузок.
- Карта полученных диапазонов хранится в памяти. Размер разреженного файла
  не используется как признак полноты. Читатель никогда не получает дырки.
- Публикация готового `<trackId>.mp3` выполняется только после получения всех
  диапазонов и успешного завершения последнего HTTP-ответа, с flush на диск
  и переносом файла. Затем применяется существующий лимит LRU.
- Закрытие DataSource при seek освобождает читателя, сохраняя текущую сессию.
- Смена трека, остановка или ошибка удаляет ненужные временные данные.
  Удаление при закрытии асинхронное, чтобы не выполнять дисковый IO в Listener
  плеера. После аварии `.part` очищаются при создании TrackCacheRepository.
- Явное «сохранить локально» использует ту же сессию и удерживает её при смене
  трека, пока не завершится сохранение. Копирование не перехватывает приоритет
  чтения у плеера. Разрушение сервиса/очистка всего потокового кэша отменяет
  также это сохранение; незавершённый постоянный файл не публикуется.
- Полная предзагрузка следующих треков из PlayerRepository отключена, пока
  подключён потоковый кэш. Предварительное открытие источников самим Media3
  обслуживается тем же координатором.

## Границы первой реализации

JavaFX подключён к общим сессиям через DesktopAudioRelay. Общий механизм диапазонов не зависит от Android.

Полный файл означает корректно полученное HTTP-тело, а не проверку декодером
каждого аудиокадра. При отсутствии ETag предполагается неизменность содержимого
одной прямой ссылки; диапазоны от разных ссылок не смешиваются.

Пользовательские Android-логи подтверждают начало звука до публикации полного файла; seek проверен пользователем на слух. Статус upstream 200/206, прокси и Windows relay пока требуют проверки в приложении.
Добавлены тесты общего механизма в shared/desktopTest и HTTP-транспорта в
yaMusicSdk/src/test. Сборка и тесты не запускались согласно AGENT.md.

## Проверка на Android после сборки

1. Открыть отсутствующий в кэше трек на медленной сети: звук должен появиться
   до полного MP3 в кэше, а `.part` расти во время воспроизведения.
2. Перемотать далеко вперёд и назад: допустима буферизация, не тишина из дырок.
3. Быстро сменить несколько треков: временные файлы старых сессий исчезают.
4. Дождаться полной загрузки и повторить запуск без сети.
5. Оборвать сеть, остановить плеер, завершить процесс и запустить снова:
   незавершённый трек не должен определяться как доступный офлайн.
6. Проверить HTTP/SOCKS-прокси и сохранение текущего трека при прослушивании.

Контракты: [Media3 DataSource](https://developer.android.com/reference/androidx/media3/datasource/DataSource),
[референс прямой ссылки ЯМ](https://github.com/MarshalX/yandex-music-api/blob/master/yandex_music/download_info.py).

## Windows loopback relay

DesktopAudioRelay использует встроенный jdk.httpserver, явно включённый в
nativeDistributions. Сервер запускается при первом незакэшированном ЯМ-треке.
Bind выполняется сразу на 127.0.0.1:0: ОС выбирает и занимает свободный порт
одним действием. Один порт используется до закрытия runtime; внешние сетевые
интерфейсы не слушаются.

Каждый выбор трека получает случайный путь .mp3; старый путь отзывается.
Обрабатываются GET/HEAD выбранного ресурса с правильным Host. JavaFX получает
Content-Length, Accept-Ranges и Content-Range для одиночного Range, включая
открытый конец и suffix. Некорректный/множественный диапазон даёт 416, старый
путь — 404, ошибка источника до отправки заголовков — 502. If-Range без
поддерживаемого валидатора приводит к полному ответу 200.

HTTP-обработчики читают общую сессию и отправляют байты по мере поступления.
Обрыв соединения JavaFX при seek освобождает читателя, но сохраняет сессию
текущего трека. Смена трека отменяет старые HTTP-запросы и прерывает ожидание.
Запрос без прогресса 30 секунд закрывается watchdog. Закрытие приложения
останавливает сервер, обработчики и общий потоковый кэш.

Прежний MediaPlayer освобождается перед отзывом адреса. Готовые файлы
открываются через file URI. Интернет-запросы выполняются только в YaMusicSDK
с настройками ЯМ-прокси; relay не загружает прямые ссылки самостоятельно.

### Логи

Фильтры: DesktopAudioRelay, TrackStream, TrackCacheRepository,
DesktopPlayerEngine. Всё попадает в существующий desktop-журнал сессии.

- [start]: loopback-адрес и порт.
- [resolve]: trackId, готовый файл либо поток.
- [request], [headers]: requestId, метод, HTTP-статус и обслуживаемый диапазон.
- [firstBytes]: время до первой отправленной порции; [wait] — чтение,
  ожидавшее данные не менее 200 мс.
- [complete]: завершён HTTP-ответ, который может содержать только часть трека.
- [range] / [headers] тега TrackStream: запрошенные и полученные границы upstream.
- [streaming]: опубликован полный MP3.
- [disconnect]: JavaFX закрыл чтение, что нормально при seek.
- [cancel], [timeout], [error]: отмена, отсутствие прогресса или сбой с этапом,
  типом исключения и количеством отправленных байтов.
- [seekTo], [ready], [playing], [stalled]: команда seek и состояние JavaFX.
- [close] тега TrackStream: удаление временного файла; DesktopAudioRelay —
  остановка сервера и освобождение порта.

Прямые ссылки ЯМ, токены и случайные пути relay не логируются.

### Проверка Windows после сборки

и назад, быстро сменить несколько треков. Сопоставить [seekTo] с Range:
JavaFX может обслужить seek из собственного буфера без HTTP-запроса.
Проверить готовый кэш без сети, ЯМ-прокси, закрытие приложения и packaged
EXE/MSI с модулем jdk.httpserver.
