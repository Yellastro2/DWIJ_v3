# Ограничения запросов Яндекс Музыки

Реализовано 2026-10-12 в `yaMusicSdk/.../network/YamRateLimiter.kt` и
`YamHttpTransport.execute`. Общая пауза относится к API текущего OAuth-аккаунта,
не к аудиопотоку. Без 429 обычные запросы выполняются параллельно.

## Пауза и восстановление

- Локальные интервалы: **3 → 5 → 10 → 30 → 60 секунд**; следующие отказы
  используют 60 секунд. Это настройки клиента, не известные лимиты Яндекса.
- `Retry-After` в секундах или формате HTTP-даты увеличивает паузу, если
  сервер просит ждать дольше. Заголовок читается до декодирования тела ошибки.
- Параллельные ответы 429 одной группы запросов увеличивают ступень только
  один раз. Поздний успех уже летящего запроса не снимает ограничение.
- После паузы выполняется один пробный запрос. Затем запросы проходят
  последовательно с промежутком 250мс; пять успешных HTTP-ответов завершают
  восстановление. Повторный 429 снова увеличивает паузу.
- Ожидание отменяемое. Отмена пробного запроса освобождает слот.
  При смене аккаунта старые ожидающие операции прекращаются; перед отправкой
  транспорт также проверяет, что OAuth-токен не изменился.

## Политики

| Операция | Поведение при 429 |
| --- | --- |
| GET API, POST `/tracks` (чтение метаданных) | Общая пауза, максимум два повтора |
| Лайк, снятие лайка, «не рекомендовать» | Общая пауза, максимум пять повторов |
| `/play-audio`, rotor feedback | Один вызов; события во время паузы или занятого пробного слота пропускаются, очереди нет |
| Другие POST, включая изменения плейлистов | Ждут общую паузу, отправляются один раз |
| `download-info`, аудиодиапазоны, внешний контент | Вне общей паузы и повторов API |

Повтор реакции разрешён только после явного HTTP 429. Таймауты, сетевые ошибки
и другие HTTP-отказы POST не повторяются. Существующие повторы GET после
таймаута подключения остаются отдельным механизмом.

После истечения паузы новое событие тоже может стать пробным запросом.
Поэтому API способен восстановиться при обычном прослушивании без открытия
каталога; ранее пропущенные события повторно не отправляются.

Плеер сохраняет существующее состояние ожидания реакции и не принимает
дублирующее нажатие до завершения операции. Состояние в Room обновляется
по подтверждённому сервером списку лайков. Новая постоянная очередь реакций
не создаётся; ожидание ограничено текущим вызовом и его coroutine scope.

## Диагностика и проверка

`YamNetwork [recordLimit]` показывает ступень, оставшуюся паузу и разобранный
`Retry-After`; `[execute]` — номер повтора; `[acquire]` — пропуск события;
`[release]` — восстановление API. Токены и тело ответа не логируются.

`YamRateLimiterTest` проверяет интервалы и предел повторов, обе формы
`Retry-After`, объединение параллельных 429, освобождение пробного слота при
отмене, пропуск событий и независимость аудио. Gradle и тесты агентом
не запускались; сборка и проверка на устройстве остаются за пользователем.

Стандарт: [HTTP 429 и Retry-After](https://www.rfc-editor.org/rfc/rfc6585.html#section-4).
HTTP 429 подтверждает ограничение запросов, но сам по себе не объясняет
правило Яндекса, срок блокировки или источник повышенной нагрузки.
